# Go-бэкенд

Реализованы публичные HTTP-ручки, PostgreSQL/pgvector, приватный MinIO и
Python-инференс с весами из `core/weights`. Контракт — `api/openapi.yaml`.
Сначала меняется OpenAPI, затем `go generate ./...`, затем реализация.
`api/api.gen.go` и `internal/mlapi/client.gen.go` не редактируются вручную.

## Запуск

Из корня репозитория, с запущенным Docker:

```sh
docker compose up -d --build
docker compose ps
```

`.env` необязателен для локального запуска: Compose содержит defaults.
Для своих настроек скопируйте `.env.example` в `.env`. Первая сборка скачивает
образы и зависимости; готовый ML-контейнер не скачивает веса при запуске.

- API: `http://localhost:8080`.
- Готовность: `http://localhost:8080/readyz`.
- OpenAPI: `http://localhost:8080/openapi.json`.
- MinIO console: `http://localhost:9001`.
- [Инструкция для фронтенда и примеры fetch](FRONTEND.md).

`BACKEND_PORT` меняет внешний порт, `CORS_ALLOWED_ORIGINS` — разрешённые origin
фронтенда. Это локальный MVP без авторизации; перед публикацией в интернете
нужно отдельно настроить доступ.

Для разработки Go вне Docker: Go 1.26+, окружение из `.env.example`, доступные
PostgreSQL/MinIO/ML, затем `cd backend && go run ./cmd/server`.
Приложение читает окружение процесса, не загружает `.env` автоматически.
ML по умолчанию не публикует порт наружу; полный запуск через Compose проще.

## Проверки

Без инфраструктуры, из `backend`:

```sh
go generate ./...
go test ./...
go vet ./...
go build ./...
```

С PostgreSQL/MinIO, из корня (тесты внутри Docker-сети, включая race detector):

```sh
docker compose --profile test run --rm --build backend-test
docker compose exec -T ml python -m unittest core.test_server
python scripts/smoke.py
```

`smoke.py` требует Python 3, только стандартную библиотеку. Проверяет все
12 операций на настоящем ML/MinIO/PostgreSQL: загрузку/скачивание, признаки,
галерею, пагинацию, поиск, исключения, удаление, валидацию, CORS и состояние.
Созданные наблюдения удаляются; один маленький тестовый кадр остаётся,
поскольку API удаления кадров нет. Это проверка интеграции,
не качества распознавания на автомобильном датасете.

Интеграционные Go-тесты создают уникальную временную схему PostgreSQL и бакет
MinIO, затем удаляют только свои ресурсы. Для запуска с хоста задайте
`TEST_DATABASE_URL`, `TEST_S3_ENDPOINT`, при необходимости `TEST_S3_ACCESS_KEY_ID`,
`TEST_S3_SECRET_ACCESS_KEY`. Без этих переменных интеграционные тесты явно
пропускаются. Если localhost:5432 занят другой БД, используйте Docker-тестовый
контейнер либо измените `POSTGRES_PORT`.

## Архитектура

| Каталог | Ответственность |
| --- | --- |
| `api` | Публичный OpenAPI, сгенерированные типы/клиент/strict server |
| `cmd/server` | Конфигурация, сборка зависимостей, graceful shutdown |
| `internal/service` | HTTP-валидация, CORS, сценарии галереи/поиска/признаков |
| `internal/storage` | PostgreSQL, миграция, S3/MinIO |
| `internal/mlapi` | Внутренний OpenAPI и сгенерированный Go-клиент |
| `internal/inference` | Вызов ML с тайм-аутом и проверка версии |
| `../core/server.py` | Приватный HTTP-сервис поверх существующего extractor |

Генератор [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) закреплён
на v2.8.0, Go-зависимости — в go.mod/go.sum. JSON проверяется по схеме до
преобразования в сгенерированные типы. Дополнительно проверяются формат
изображения, BBox, конечность и норма эмбеддинга. Ошибки имеют JSON-формат OpenAPI.

## Хранение и версии модели

При старте применяется встроенная идемпотентная миграция под advisory lock.
Она работает с новой БД и со схемой из `infra/postgres/init`: добавляет размеры
кадров, индекс пагинации и запись версии модели. Данные не удаляются.
Если старые наблюдения не имеют версии модели, размеров кадра или ссылки на
кадр, запуск завершается с диагностикой: записи нужно восстановить или
переиндексировать, они не смешиваются с новой галереей.

`MODEL_VERSION` обозначает пару весов и препроцессинга; меняйте её при изменении
любого из них. Смена версии на непустой несовместимой галерее отклоняется.
`image_id`, `vehicle_id`, `model_version` хранятся в metadata.
confidence — свойство пары запрос/наблюдение, вычисляется при поиске.
Сортировка галереи — created_at DESC, id DESC; пагинация курсорная.

Поиск использует HNSW/cosine distance с итеративным сканированием pgvector 0.8+;
`confidence = 1 - distance`. Исключения применяются до top-K. При нехватке
кандидатов после ANN используется точный поиск, чтобы не спутать исчерпание
индекса с пустой галереей. Кандидаты сортируются по убыванию сходства и UUID
при равенстве. `candidates` применяет порог >= 0.36, `ranking` порог не применяет.

Загрузка сначала сохраняет приватный объект, затем метаданные. При ошибке БД
выполняется попытка удалить объект даже после отмены клиентского запроса.
Удаление наблюдения сохраняет общий исходный кадр. Срок хранения кадров и
периодическая очистка остаются отдельной продуктовой задачей.

## Ограничения и связь с исходным ТЗ

- Go выбран по указанию пользователя; в ТЗ перечислены Python/C++/Rust.
  Инференс остаётся на Python.
- Нет детекции, OCR, трекинга; BBox передаёт клиент.
- 10 MiB/40 млн пикселей на кадр, 64 KiB на JSON, 11 MiB на multipart,
  top-K до 100 — принятые ограничения API.
- Один ML-инференс одновременно, перегрузка даёт 503. Тайм-аут ML — 45 секунд,
  общий контекст запроса — 60 секунд.
- Порог 0.36 взят из существующего кода; качество порога и ReID-метрики этим
  этапом не подтверждаются. Сходство не является вероятностью.
- Offline-скрипты и CSV/NPY не менялись. Экспорт и кросс-камерная оценка остаются
  задачей offline-пайплайна. В API нет camera_id, отсутствующего в исходных данных.
- Serving-зависимости находятся в `core/requirements-serving.txt` с версиями;
  исследовательский `requirements.txt` остаётся без фиксации версий.
